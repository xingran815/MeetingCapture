# M3.1 — Lighter hooks, test levels and CI

**Goal:** routine checks take seconds where they can, and review agents run by risk, with the merge gates kept. Issue 16, branch `m3.1-faster-checks`, one PR. Why: D-61.

Measured before this milestone, from 8 CI runs in one day, so a small sample: a CI run took 5 to 6 minutes, mostly compiling; the 460 unit tests took 21 s; `check --fast` about 32 s; a full `check` 223 s.

## Hooks
| Hook | Runs |
|---|---|
| pre-commit | On staged files: format, lint, secret sweep |
| commit-msg | Commit-message sweep, unchanged |
| pre-push | On outgoing commits: identity and leak sweeps, then unit tests |

- Lint judges the staged text, not the working copy.
- The `feature/coding-interview` block stays in the pre-push hook, and also checks outgoing commits against `scripts/protected-commits.sha256`, so a renamed copy is refused even with the original branch gone (D-62). The written rules stay in `CLAUDE.md` too: never push or merge that branch, and push named refs only.
- Pre-commit no longer builds, so a commit may not compile. Pre-push catches it.

## Local test levels (`scripts/check.sh`)
| Mode | Contents | When |
|---|---|---|
| `--unit` | Build and unit tests | Automatically at every pre-push |
| `--production` | Unit, the fake-CLI guard check, short E2E | By judgment, usually when capture, the pipeline or file deletion changes |
| `--full` | Production, `e2e-full`, sweep and lint self-tests | Before the milestone's final push |
| `--live` | Full plus small real calls | By hand only |

- Plain `check.sh` runs `--production`.
- These levels leave out lint and sweeps, because the hooks run them.
- `--full` saves its commit and result in `dev/tmp/`.

## Timing
`check.sh` and `ci.sh` log step names and seconds only: locally to the gitignored `dev/tmp/`, on CI to the job log.

## CI
| Trigger | Runs |
|---|---|
| PR, including docs and evidence | All 7 jobs, with a build cache |
| Push to `main` | Clean build with no cache, unit tests, leak and identity checks, then saves the build as the cache |

Docs and evidence get no special rules. `main` saves the cache because a PR can only reuse caches from its own branch or `main`.

## Review rules
| Agent | When |
|---|---|
| Verifier | Every milestone. It doesn't rerun the full test: it reads the saved record, checks the commit matches the last code change, and checks each Done-when |
| Deep review | M3, M4 and M6 at minimum, and any milestone with code that can lose recordings, delete files, or has tricky concurrency |
| Security review | Changes to credentials, data leaving the machine, subprocesses, workflows or dependencies |
| Normal reviewer | Any milestone end without a deep review |

- The merge rule keeps: CI green on the exact commit, and required agents covering all code changes.
- The merge rule adds: after a fix, re-check only the changed lines. There are two rounds to fix; if the same function fails twice, stop and ask the user.
- Remove the "CI and the review agents together" section and its rules-table row from `CLAUDE.md`. Agents then run after CI unless a spec says otherwise. The M3 and M6 specs keep running the security and deep reviews in parallel with each other.
- The same rule also goes from two files outside this repo: the project memory `verifier_alongside_ci.md` with its `MEMORY.md` line, and the global `next` skill. Do this when M3.1 merges and report it separately, since the PR won't show it.
- **Until M3.1 merges, the current rules apply.**

## Docs
- Update `CLAUDE.md`, `dev/PLAN.md`'s review table, and the specs that name the old hooks or review timing.
- Change any self-tests that expect the old hook behaviour.
- Commit docs and evidence together in one commit.

## Done when
- [ ] A commit with a bad format or a seeded secret is refused in seconds, and a staged-versus-working-copy mismatch is judged on the staged text.
- [ ] A push with a seeded leak, a bad identity or a failing unit test is refused.
- [ ] Each `check.sh` mode runs what its table row says, and a seeded failure stops it.
- [ ] Timing logs appear locally and on CI, holding only step names and seconds.
- [ ] The second CI run on the PR is faster, with before and after times recorded. If the cache saves little, report that instead of claiming the saving.
- [ ] Pushing to `main` passes `protect-main` using the PR's 7 results, and the `main` run saves a cache that a new PR can read.

## Risks
- The last check can only be proven by the merge itself. If `protect-main` refuses the push, nothing is lost: stop and ask.
- A cache from `main` only exists after this merges, so the first PR that can reuse it is the next milestone's. On this PR, only reruns on the branch can show a saving.
- Cache savings are an untested estimate: checkout resets file times, so SwiftPM may recompile anyway.
- `swift test --parallel` is left out: it saves little and is unproven.
